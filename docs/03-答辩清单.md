## 3. 推荐演示路线

### 3.1 一分钟总览

1. 打开登录页，说明系统面向制造现场质量追踪。
2. 登录 `admin`。
3. 展示质量看板：批次、检验、缺陷、召回、趋势图和 Pareto 图。
4. 说明系统不是静态页面，数据来自 MySQL，前后端通过真实接口联调。

### 3.2 主数据与数据库设计

推荐页面：`主数据维护`

演示点：

- 物料按原材料、半成品、成品分类。
- BOM 表达物料构成关系。
- 工艺路线表达生产步骤。
- 检验标准区分 IQC、IPQC、FQC。
- 新增、编辑、删除、分页和筛选都走后端接口。

答辩口径：

> 主数据是后续批次追溯的基础。BOM 决定物料消耗关系，工艺路线决定工序记录，检验标准决定检验任务需要填写哪些项目。

### 3.3 批次台账

推荐页面：`批次台账`

演示点：

- 原材料批次、半成品批次、成品批次统一登记在 `batch` 表。
- 批次状态包括待检、检验中、合格、冻结、已耗尽、已召回等。
- 批次详情能看到检验历史、缺陷、消耗和出货去向。

可重点展示：

- `RM-20260610-001`：召回源头批次。
- `FP-20260614-001`：已出货并被召回的成品批次。
- `FP-20260624-001`：使用合格温控器，不在召回影响面内的对照批次。

### 3.4 生产工单

推荐页面：`生产工单`

演示点：

- 工单创建时校验物料、BOM、工艺路线和 FQC 标准。
- 领料会扣减原材料或半成品批次余量，并写入 `batch_consumption`。
- 工序必须按顺序开工和完工。
- IPQC 工序未通过时，后续工序不能继续。
- 完工入库后生成产出批次，并自动创建 FQC 检验任务。

答辩口径：

> 追溯链不是事后手工填写，而是在领料、工序、完工入库这些业务动作中自动沉淀出来。

### 3.5 检验与缺陷闭环

推荐页面：`检验任务`、`缺陷管理`

演示点：

- IQC 对来料批次检验。
- IPQC 对关键工序检验。
- FQC 对成品或半成品完工批次检验。
- 检验结论会联动批次和工序状态。
- 不合格或让步接收会同步产生缺陷记录。
- 缺陷支持返工、报废、让步、退货等处置方式。

答辩口径：

> 检验任务、检验明细和缺陷记录是质量闭环。系统不只记录结果，还通过状态机限制后续业务能否继续。

### 3.6 出货、追溯与召回

推荐页面：`出货管理`、`追溯查询`、`召回管理`

推荐演示顺序：

1. 进入追溯查询。
2. 查询 `RM-20260610-001` 的下游。
3. 展示它影响了 `FP-20260614-001` 和 `FP-20260620-001`。
4. 说明 `FP-20260624-001` 不在影响面内，因为它使用的是另一批合格温控器。
5. 进入召回管理，展示召回单和召回明细。
6. 展示已出货明细关联客户，在库明细不关联出货单。

答辩口径：

> 反向追溯用于从成品查原料和供应商，正向追溯用于从问题原料查受影响成品和客户。召回模块复用正向追溯结果自动生成影响面，减少漏召回风险。

### 3.7 统计报表

推荐页面：`统计报表`

演示点：

- 合格率趋势按自然月统计。
- 缺陷 Pareto 展示主要缺陷类型。
- 供应商质量分析同时看 IQC 合格率、缺陷数和召回数。

答辩口径：

> 统计报表不是单独维护的数据，而是从检验、缺陷、供应商和召回业务表聚合得到。

## 4. 数据库得分点

### 4.1 表设计

- 系统包含 20 张业务表和 1 张单号流水技术支撑表。
- 批次 `batch` 是追溯基本单元。
- 批次消耗 `batch_consumption` 是追溯链的边。
- 检验任务、检验明细、缺陷、出货、召回围绕批次展开。
- 外键使用 `RESTRICT`，避免误删历史质量记录。

### 4.2 ER 与规范化

答辩口径：

> 系统按权限域、主数据域、生产追溯域、质量检验域、出货召回域分解建模，再整合为全局 ER。核心实体之间没有把多值字段塞到一张大表里，关系模式满足课程要求的规范化设计。

### 4.3 递归 CTE

答辩口径：

> 追溯查询使用 MySQL 递归 CTE。反向追溯从成品批次沿 `production_order` 和 `batch_consumption` 找上游原料；正向追溯从原料批次沿消耗关系找到下游产出批次，再关联出货记录定位客户。

### 4.4 触发器、视图和存储过程

可说明：

- 触发器用于兜底冻结不合格批次。
- 视图用于封装批次台账和统计口径。
- 存储过程封装数据库层追溯能力。
- 应用层事务负责复杂业务一致性，数据库约束负责最终兜底。

### 4.5 单号并发

答辩口径：

> 批次号、工单号、检验单号、缺陷编号、出货单号、召回单号统一由 `serial_number` 表分配。通过 MySQL 行锁和业务唯一约束保证同一日期前缀下不会重复或断号。

## 5. 后端得分点

- 统一响应结构：`Result{code,message,data}`。
- JWT 登录认证，角色控制接口权限。

- Swagger 自动生成接口文档。
- Druid 用于连接池和 SQL 监控。

## 8. 常见问题回答

### Q1：为什么批次是核心？

因为质量追溯关注的是某一批原料、半成品或成品的来源、去向和质量状态。系统所有生产、检验、缺陷、出货、召回都围绕批次展开。

### Q2：为什么不只做成品追溯？

只做成品追溯无法定位问题源头。系统同时管理原材料、半成品和成品批次，可以从成品反查原料，也可以从问题原料正查受影响客户。

### Q3：为什么需要三级检验？

IQC 控制来料质量，IPQC 控制生产过程质量，FQC 控制完工出厂质量。三级检验对应制造现场常见质量控制节点。

### Q4：为什么召回明细要关联出货记录？

已出货批次需要定位客户和出货数量，所以明细关联 `shipment`；在库受影响批次没有客户流向，因此 `shipment_id` 可以为空。

### Q5：为什么不用删除历史业务数据？

质量追踪强调审计和责任链，批次、检验、缺陷、出货、召回都是历史证据。删除会破坏追溯链，所以数据库外键和业务规则都限制误删。

### Q6：为什么有些业务由后端校验，而不是只靠前端？

前端校验只能改善体验，不能保证数据安全。关键规则必须在后端事务中校验，并由数据库约束兜底。

### Q7：如果老师问系统是否可真实运行，怎么回答？

可以说明系统不是静态原型：后端连接 MySQL，前端调用真实接口；项目提供数据库初始化脚本、Swagger、Druid、构建命令、接口巡检、前端巡检、E2E 流程和截图生成脚本。
